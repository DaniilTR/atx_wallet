# Обоснование выбора самого безопасного варианта обмена (Swap)

## Контекст проекта
В текущем проекте обмен в UI существует как «предпросмотр» (расчёт по ценам), но фактического on-chain swap пока нет.

Цель этого документа — объяснить, почему **самый безопасный вариант с точки зрения информационной безопасности** для реализации swap в некастодиальном кошельке — это **прямое взаимодействие с DEX Router контрактом (например, Uniswap/Sushi) через RPC с локальной подписью транзакций**, без WebView-виджетов и без зависимости от сторонних сервисов, которые формируют calldata.

## Что считаем “безопасностью” (информационная безопасность)
Под “инфобезом” здесь подразумеваются риски:

- **Компрометация секретов**: сид-фразы/приватные ключи/подписывающие операции.
- **Утечки метаданных**: адреса, пары обмена, суммы, IP/идентификаторы устройства, телеметрия.
- **Supply-chain/встраивание стороннего кода**: SDK/виджеты, WebView, внешние скрипты.
- **Атаки на канал**: MITM, подмена ответов, злоупотребление доверенными endpoint’ами.
- **Расширение поверхности атаки**: дополнительные компоненты, плагины, разрешения, сложные зависимости.

Этот документ не про “финансовую безопасность” (например, MEV/фронт‑ран, проскальзывание, экономические атаки на DEX). Эти риски тоже важны, но они отдельным слоем.

## Рассмотренные варианты
Сравнивались три подхода:

1. **DEX Router напрямую (Uniswap/Sushi) через `web3dart`**: котировки/вызовы смарт‑контракта, формирование `Transaction.callContract`, локальная подпись, отправка в сеть.
2. **Агрегатор 1inch через HTTP API**: получение quote и/или “готовых” данных транзакции (`to`, `data`, `value`, `gas`), затем локальная подпись и отправка.
3. **Сторонний виджет/SDK (часто через WebView)**: интеграция UI/SDK провайдера обмена/покупки.

## Выбранный вариант: прямой Router swap с локальной подписью
### Почему он “самый безопасный” по инфобезу

#### 1) Минимум доверия к третьим сторонам
При прямом вызове Router:
- приложение взаимодействует с **RPC** и **известными адресами контрактов**;
- не нужно доверять внешнему сервису, который “собирает” calldata и может вернуть транзакцию на неожиданный адрес.

Снижается риск класса атак “подмена транзакции на стороне провайдера котировки/виджета”.

#### 2) Меньше внешних интеграций → меньше поверхность атаки
- Нет WebView (встроенный браузер обычно резко увеличивает attack surface).
- Нет необходимости подключать тяжёлый сторонний SDK/виджет.
- Меньше зависимостей → меньше supply-chain рисков.

#### 3) Секреты остаются на устройстве
Ключевой принцип: **подпись транзакции выполняется локально**.
- Ни приватный ключ, ни сид-фраза не должны покидать устройство.
- Вариант Router это поддерживает “по умолчанию”: вы формируете tx → подписываете → отправляете.

(Важно: это верно и для 1inch, если соблюдать локальную подпись. Но 1inch добавляет дополнительную точку риска: внешний сервис формирует calldata.)

#### 4) Больше возможностей для строгой валидации
С прямым Router проще внедрить allowlist и проверки:
- разрешённые адреса Router контрактов;
- проверка chainId, token addresses, recipient;
- ограничение/политика approve (например, не выдавать бесконечные approvals, использовать минимально необходимый allowance).

#### 5) Контроль сетевого контура
Даже в “прямом” варианте остаётся внешняя зависимость: RPC.
Но её легче контролировать:
- можно использовать собственный RPC/прокси;
- можно централизованно применять защитные меры (rate limit, мониторинг, фильтрация).

## Почему не 1inch (как “самый безопасный”)
1inch может быть отличным вариантом для MVP, но с точки зрения инфобеза он обычно хуже прямого Router подхода, потому что:

- **Добавляется внешний HTTP‑провайдер**, который видит метаданные (пары, суммы, IP) и потенциально может быть точкой компрометации.
- **Риск подмены/манипуляции ответом**: если приложение некорректно валидирует `to/data/value`, можно подписать нежелательную транзакцию.

При этом 1inch можно сделать достаточно безопасным при строгой валидации и локальной подписи — просто это всё равно остаётся “ещё один важный внешний компонент”.

## Почему не виджет/SDK (как “самый безопасный”)
Виджеты/SDK (особенно через WebView) в среднем наиболее рискованные по инфобезу:

- WebView увеличивает поверхность атаки (инъекции, подмена контента, слабые настройки, сложность контроля JS‑окружения).
- Сторонний код может собирать телеметрию/идентификаторы/события.
- Часто есть дополнительные юридические/регуляторные процессы (особенно для фиат‑покупок), что означает обработку персональных данных.

Этот вариант может быть “быстрее в релиз”, но он не “самый безопасный” именно в плане информационной безопасности.

## Предпосылки и допущения
Этот выбор корректен при допущениях:

- кошелёк **некастодиальный** (ключи у пользователя);
- транзакции **подписываются локально**;
- адреса Router/токенов берутся из доверенного источника (конфиг/allowlist), а не из непроверенного API;
- реализованы базовые проверки (slippage, deadline, approve‑политика).

Если часть допущений не выполняется, “самый безопасный” выбор может измениться.

## Рекомендации по усилению инфобеза для Router swap
Минимальный список практик, которые делают выбранный вариант действительно безопасным:

- **Allowlist контрактов**: разрешать вызовы только на известные Router адреса для конкретного `chainId`.
- **Approve‑политика**: по умолчанию делать approve на точную сумму/лимит, избегать unlimited allowance.
- **Проверки параметров**: `chainId`, `to`, `value`, recipient, amountOutMin/slippage.
- **Сетевой слой**: по возможности свой RPC или прокси; минимум логирования; осторожно с аналитикой.
- **Изоляция секретов**: хранение в secure storage, отсутствие debug‑логов секретов, запрет отправки ключей в сеть.

## Итог
С точки зрения информационной безопасности, самый безопасный вариант — это **прямой on-chain swap через DEX Router при локальной подписи транзакций**, потому что он:

- минимизирует доверие к внешним поставщикам данных/виджетов,
- уменьшает поверхность атаки (особенно за счёт отказа от WebView/SDK),
- оставляет секреты и контроль подписи на устройстве,
- позволяет внедрить строгие allowlist‑проверки на уровне приложения.

## Возможные уязвимости и риски (даже в выбранном варианте)
Ниже перечислены типовые уязвимости/риски, которые остаются релевантными даже при “самом безопасном” архитектурном выборе. Это полезно понимать заранее, чтобы не получить ложное чувство защищённости.

### 1) Компрометация секретов на устройстве
**Риск:** утечка сид‑фразы/приватного ключа из памяти, логов, небезопасного хранилища или из-за компрометации ОС.

Типовые причины:
- хранение сид‑фразы/ключей в plaintext (файлы, SharedPreferences и т.п.);
- отладочные логи, дампы, краш‑репорты, которые случайно содержат секреты;
- malware/рут/джейлбрейк, overlay‑атаки, accessibility‑сервисы на Android;
- скриншоты/запись экрана на чувствительных экранах.

**Меры снижения:** secure storage (Keychain/Keystore), запрет логирования секретов, защита экранов (anti‑screenshot/secure flag на чувствительных view), детект рут/джейлбрейк (как сигнал риска), минимизация времени жизни ключа в памяти, по возможности — подпись в изолированном модуле/secure enclave.

### 2) Ошибки формирования транзакции swap
**Риск:** приложение формирует транзакцию с неверными параметрами (не тот `chainId`, неверные адреса токенов/Router, неверный recipient, неверный `amountOutMin`), что приводит к потере средств или неожиданному поведению.

Типовые причины:
- неверная/непроверенная таблица адресов контрактов (Router/Token);
- подмена конфигурации в рантайме (например, если адреса берутся из сети);
- несоответствие ABI фактической версии Router;
- ошибки округления и работы с decimals.

**Меры снижения:** жёсткий allowlist (Router адреса для конкретного `chainId`), валидация параметров перед подписью, строгая типизация и работа с базовыми единицами (wei / минимальные единицы токена), unit‑тесты на кодирование calldata, обязательный “confirm screen” с отображением: сеть, `to`, токены, суммы, лимит проскальзывания.

### 3) Уязвимости вокруг `approve` (allowance)
**Риск:** `approve` — одна из самых частых причин потерь в DeFi, потому что выдаёт право тратить токены “spender’у”.

Типовые проблемы:
- unlimited allowance (бесконечный approve) на Router/контракт, который потом может быть скомпрометирован;
- approve на неверный адрес (подмена Router адреса);
- “approval race”/некорректная смена allowance (старые ERC‑20 иногда требуют сначала выставить 0);
- токены с нестандартным поведением ERC‑20 (возвраты `false`, комиссии на перевод и т.п.).

**Меры снижения:** политика минимального allowance (approve ровно под нужный amount + небольшой буфер), allowlist spender адресов, безопасная процедура изменения allowance (при необходимости: сначала 0, потом новое значение), отдельный экран подтверждения approve с понятным предупреждением.

### 4) Риски RPC-провайдера и сетевого канала
**Риск:** даже без агрегаторов приложение зависит от RPC узла. Компрометация/подмена RPC или сетевого канала может привести к:
- неверной информации при чтении (balances, decimals, allowance, nonce, gas price);
- навязыванию завышенных комиссий (подмена gas price/fee параметров);
- цензуре/DoS (транзакции не проходят).

**Меры снижения:** HTTPS RPC, по возможности свой RPC/прокси, таймауты и ретраи, fallback на несколько RPC (с согласованием по `chainId`/номер блока), минимизация доверия к значениям gas (лимиты/санити‑чеки), логирование ошибок без персональных данных.

### 5) Риски смарт‑контрактов (Router/Token)
**Риск:** on-chain взаимодействие безопасно “как протокол”, но контракты могут иметь уязвимости или быть подменены (например, через неправильный адрес или через прокси‑обновления).

**Меры снижения:** использовать только широко проверенные Router адреса для конкретной сети; не брать адреса “с интернета” без верификации; хранить allowlist в приложении и обновлять его контролируемо; в идеале — проверять, что `to` совпадает с ожидаемым адресом и сеть корректна.

### 6) Supply-chain риски зависимостей и сборки
**Риск:** компрометация зависимостей (Dart packages, нативные зависимости, build scripts) может привести к утечке секретов, внедрению вредоносного кода, перехвату транзакций.

**Меры снижения:** pin версий (lockfile), контроль обновлений, минимизация зависимостей, проверка репутации пакетов, включение SAST/Dependency scanning, запрет несанкционированных сборочных скриптов, разделение dev/prod ключей.

### 7) Фишинг и социальная инженерия через UI
**Риск:** пользователь может быть обманут через подмену адресов/токенов/сетей (похожий символ токена, подмена адреса получателя, QR‑подмена).

**Меры снижения:** отображение адресов в checksum‑форме, предупреждения при подозрительных токенах, явное отображение сети/chainId, подтверждение ключевых параметров перед подписью, ограничения на автоподстановки из буфера/QR без подтверждения.

### 8) Утечки метаданных и приватность
**Риск:** даже при прямом swap метаданные видны:
- RPC‑провайдеру (IP, адрес, запросы);
- публичному блокчейну (адреса, суммы, контракты).

**Меры снижения:** свой RPC/прокси, минимизация запросов, отключаемая аналитика, аккуратная телеметрия без адресов/сумм, использование нескольких RPC или приватных RPC‑провайдеров.

### 9) Ошибки управления nonce/chainId и replay‑риски
**Риск:** неверный `chainId` или некорректная работа с nonce может приводить к:
- невозможности отправки;
- “залипанию” транзакций;
- в худших сценариях — replay на другой сети при неправильной подписи (если не использовать EIP‑155 корректно).

**Меры снижения:** всегда подписывать с корректным `chainId`, получать nonce из сети, обрабатывать замены транзакций (speed‑up/cancel) аккуратно, не смешивать сети в одном окружении.

## Вывод по уязвимостям
Выбор “Router напрямую + локальная подпись” снижает риски, связанные со сторонними виджетами/SDK и внешними сервисами формирования транзакций, но **не отменяет** основные классы инфосек‑рисков: компрометация устройства, ошибки реализации, supply‑chain, RPC‑зависимость и фишинг через UI.
