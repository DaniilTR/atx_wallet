## 1) Текущие вводные проекта (из кода)
- EVM RPC endpoint: `kEvmRpcUrl` (по умолчанию `https://ethereum.publicnode.com`).
- EVM chainId: `kEvmChainId` (по умолчанию `1` – Ethereum mainnet).
- В проекте уже есть `BlockchainService` (отправка native/ERC‑20) и `WalletProvider` (балансы/цены/история).
- UI swap уже существует как “предпросмотр” в `swap_sheet.dart`, но реального swap нет.

### 1.1 Выбранный DEX кассир (Router)
Используем **Uniswap V2 Router02**.

- Router (Ethereum Mainnet, `chainId=1`): `0x7a250d5630B4cF539739dF2C5dAcb4c659F2488D`
- WETH (Ethereum Mainnet): `0xC02aaA39b223FE8D0A0E5C4F27eAD9083C756Cc2`

Важно: в текущем проекте `USDT` задан адресом **Ethereum mainnet**. Поэтому swap корректно поддерживается только при `kEvmChainId == 1` (или при отдельном наборе токенов/allowlist на другие сети).

## 2) Высокоуровневая архитектура реализации
### 2.1 Компоненты
Планируется добавить/расширить следующие слои (без WebView и без сторонних SDK):

- **Swap domain/service слой**
  - `SwapService` (интерфейс): `quote()`, `buildSwapTx()`, `executeSwap()`.
  - Реализация `UniswapV2RouterSwapService` (или аналог для выбранного Router).

- **On-chain слой**
  - Расширение `BlockchainService`:
    - чтение `allowance`/`nonce`/`eth_getCode` (через `web3dart`),
    - отправка транзакций swap (callContract) с корректным `chainId`.
  - `Erc20Service` для `allowance()` и `approve()` (ABI ERC‑20).
  - `RouterService` для `getAmountsOut()` и swap методов (ABI Router).

- **Конфигурация и allowlist**
  - `RouterAllowlist`: список разрешённых Router адресов **по chainId**.
  - `TokenAllowlist`: список разрешённых токенов/контрактов (используем уже существующий `TokenMetadata`, но запрещаем произвольные “custom tokens” без верификации).

- **UI/UX слой (swap_sheet)**
  - Добавить 2‑фазный сценарий:
    1) Quote/Preview (обновляется при изменении суммы/пары),
    2) Confirm (подробности + предупреждения + подтверждение).

### 2.2 Сценарий “swap” (основной поток)
1) Пользователь выбирает `fromToken`, `toToken`, сумму.
2) Приложение получает quote:
   - on-chain `router.getAmountsOut(amountIn, path)` (для Router V2),
   - рассчитывает `amountOutMin` с учётом slippage.
3) Перед выполнением swap:
   - проверяет chainId,
   - проверяет allowlist адресов,
   - проверяет баланс,
   - для ERC‑20 проверяет `allowance`.
4) Если allowance недостаточен — предлагает approve:
   - отдельный экран подтверждения approve,
   - approve на ограниченную сумму.
5) Формирует swap‑транзакцию и показывает экран подтверждения (сеть/адрес Router/суммы/лимиты).
6) Локально подписывает транзакцию и отправляет в сеть через RPC.
7) Сохраняет запись в историю/показывает статус.

## 3) Минимизация рисков (2–9): меры и проверки

### 2) Ошибки формирования транзакции swap
**Риск:** неверные адреса/chainId/параметры, ошибки decimals и округления → неожиданное поведение/потери.

**Меры минимизации (конкретно):**
- **Жёсткая конфигурация allowlist**
  - Router адреса задаются статически для каждого `chainId`.
  - Токены берутся из поддерживаемого набора (`TokenMetadata`) + контрактные адреса верифицированы.
- **Единицы измерения**
  - Все суммы для calldata формируются как `BigInt` в базовых единицах (wei/минимальные units).
  - Конвертация `double → BigInt` выполняется единообразно и покрывается тестами.
- **Валидация перед подписью**
  - Проверка: `chainId == kEvmChainId`.
  - Проверка: `tx.to` совпадает с разрешённым Router адресом.
  - Проверка: recipient = текущий адрес кошелька (или явное подтверждение, если иной).
  - Санити‑чеки: `amountIn > 0`, `amountOutMin > 0`, `deadline` в разумных пределах.
- **Проверяемость**
  - Unit‑тесты на построение calldata (как минимум: правильные параметры и порядок).
  - Интеграционный прогон на тестнете/форке (при наличии окружения).

### 3) Уязвимости вокруг `approve` (allowance)
**Риск:** неограниченный allowance или approve на неверный адрес.

**Меры минимизации (конкретно):**
- **Approve только на нужную сумму**
  - Стратегия по умолчанию: approve ровно `amountIn` (+ небольшой буфер, опционально).
  - Unlimited approval выключен по умолчанию.
- **Spender allowlist**
  - `spender` = Router адрес из allowlist (по `chainId`).
  - Любой другой spender — запрет.
- **Безопасное обновление allowance**
  - Для токенов с “нестандартным” approve: если требуется, сначала `approve(0)`, затем `approve(new)`.
- **Отдельное подтверждение**
  - UI разделяет approve и swap: разные действия, разные экраны подтверждения.
  - Экран approve показывает: токен, spender (Router), сумму allowance.

### 4) Риски RPC-провайдера и сетевого канала
**Риск:** RPC возвращает неверные данные, цензура, DoS, подмена gas/nonce и т.п.

**Меры минимизации (конкретно):**
- **HTTPS + таймауты**
  - Всегда использовать HTTPS RPC.
  - Явные таймауты на сетевые операции и контролируемые ретраи.
- **Fallback RPC**
  - Список резервных RPC endpoints (опционально) и переключение при ошибках.
  - При переключении повторно проверять chainId.
- **Санити‑чеки для fee/gas/nonce**
  - Ограничения сверху на предлагаемые значения (например, max gas price/priority fee), чтобы “аномальные” ответы не приводили к непредсказуемым комиссиям.
- **Свой RPC/прокси (рекомендуемо для прод)**
  - В проде предпочтительно использовать собственный RPC или прокси для контроля логов/лимитов.

### 5) Риски смарт‑контрактов (Router/Token)
**Риск:** неверный адрес Router/Token, прокси‑подмена, взаимодействие с вредоносным контрактом.

**Меры минимизации (конкретно):**
- **Allowlist Router адресов (по chainId)**
  - Никаких “router address из интернета” или из неаутентифицированного API.
- **Проверка наличия кода по адресу (eth_getCode)**
  - Перед первой операцией: убедиться, что `getCode(router) != 0x`.
  - Аналогично для ERC‑20 контрактов из allowlist.
- **Ограничение токенов**
  - Swap доступен только для токенов из `supportedTokens`.
  - Запрет на произвольный ввод адреса токена пользователем (или только через режим “advanced” с отдельными предупреждениями, если вообще нужен).

### 6) Supply-chain риски зависимостей и сборки
**Риск:** компрометация зависимостей → внедрение вредоносного кода.

**Меры минимизации (конкретно):**
- **Фиксация версий**
  - Использовать `pubspec.lock`, не допускать “плавающих” зависимостей для прод.
- **Минимизация зависимостей**
  - Для swap использовать уже имеющиеся пакеты (`web3dart`, `http` при необходимости), не тащить новые тяжёлые SDK.
- **Проверка обновлений**
  - Регулярный аудит зависимостей (в CI или вручную): что обновилось, почему, какой риск.
- **Безопасные сборки**
  - Разделение dev/prod конфигов через `--dart-define`.
  - Запрет на включение dev‑режимов в релиз (`DEV_WALLET_STORAGE`, debug‑логи).

### 7) Фишинг и социальная инженерия через UI
**Риск:** пользователь подтверждает не то (не та сеть, не тот токен, подмена адресов).

**Меры минимизации (конкретно):**
- **Экран подтверждения перед подписью**
  - Показать: сеть (chainId + имя), Router адрес (checksum), from/to токены, amountIn, expectedOut, amountOutMin, slippage, deadline.
- **Checksum и сокращение адреса**
  - Отображать адреса в EIP‑55 checksum + короткий формат, но с возможностью раскрыть полностью.
- **Явные предупреждения**
  - Если сеть не соответствует ожидаемой, swap блокировать.
  - Если токен/адрес не из allowlist — блокировать.

### 8) Утечки метаданных и приватность
**Риск:** RPC видит запросы; публичная сеть видит on-chain активность.

**Меры минимизации (конкретно):**
- **Минимизация запросов**
  - Кешировать `decimals`, `token info`, разумно опрашивать quote.
- **Сокращение телеметрии**
  - Не отправлять в аналитику адреса/суммы/пары.
  - Ошибки логировать без персональных данных.
- **Свой RPC/прокси**
  - Для прод: свой RPC/прокси уменьшает утечки IP/паттернов провайдерам.

### 9) Ошибки управления nonce/chainId и replay‑риски
**Риск:** неверный chainId в подписи или ошибки nonce приводят к stuck tx или потенциальным replay‑сценариям.

**Меры минимизации (конкретно):**
- **Подпись с правильным EIP‑155 chainId**
  - Всегда подписывать транзакции с `chainId = kEvmChainId`.
- **Nonce management**
  - Получать nonce из сети (pending) перед отправкой.
  - Не отправлять параллельно несколько swap/approve без управления очередью.
  - Предусмотреть “ускорить/отменить” (replacement tx) как отдельную прод‑фичу (не обязательно в MVP).
- **Разделение окружений**
  - Не смешивать mainnet/testnet в одном приложении без жёсткого переключателя и визуального индикатора сети.

## 4) Пошаговый план реализации (этапы)
### Этап A — Quote (без отправки)
- Реализовать on-chain quote через Router (`getAmountsOut`) для пар из allowlist.
- Подключить quote в UI вместо текущего “convertAmount по CoinGecko”.
- Добавить slippage (фиксированно, например 0.5–1%, или настройка).

**Критерий готовности:** preview показывает корректный expectedOut и amountOutMin.

### Этап B — Approve flow
- Реализовать `allowance()` и `approve()`.
- Сделать отдельный confirm‑экран approve.

**Критерий готовности:** при недостаточном allowance приложение предлагает approve и выполняет его на ограниченную сумму.

### Этап C — Swap execution
- Реализовать сборку swap‑tx (router swapExact* функции) и отправку.
- Экран подтверждения swap с полным набором параметров.

**Критерий готовности:** swap выполняется на тестнете/форке, tx hash сохраняется, ошибки обрабатываются.

### Этап D — Hardening
- Добавить `eth_getCode` проверки для Router/Token адресов.
- Добавить fallback RPC и санити‑чеки fee.
- Добавить минимальные тесты на кодирование транзакций.

## 5) Что сознательно НЕ делаем в MVP (чтобы не расширять поверхность атаки)
- Не используем WebView/виджеты/сторонние SDK для swap.
- Не разрешаем пользователю вводить произвольные адреса токенов/Router.
- Не используем unlimited approvals.
- Не внедряем “автоматический выбор лучшего маршрута” через внешние сервисы.

## 6) Примечания по проверке и демонстрации
Для диплома/отчёта удобно фиксировать:
- список allowlist адресов и сеть (chainId),
- скриншоты confirm‑экранов approve и swap,
- пример tx hash и его расшифровку в explorer,
- описание того, какие поля валидируются перед подписью.
